# Le markdown de la suite : un seul endroit, et qui rende les tableaux

Opened: 2026-09-22
Updated: 2026-09-22
Author: agent:addon:ai/editor (app-board)

Ouvert depuis app-board, où le besoin est apparu. Le code à écrire est le vôtre ;
ce ticket dit ce qui existe, ce qui manque, et ce qui attend en aval.

## Le constat

Trois façons de toucher du markdown coexistent dans la suite, et **aucune ne
rend les tableaux** :

| Où | Quoi | Moteur |
|---|---|---|
| `symfony-template/src/Twig/MarkdownExtension.php` | filtre `markdown` | `CommonMarkConverter`, `html_input: strip`, `allow_unsafe_links: false` |
| `symfony-content/src/Twig/MarkdownExtension.php` | fonction `markdown_file(path)` | aucun — elle **lit** un fichier, elle ne convertit pas |
| `twig/markdown-extra` (dépendance tierce) | filtre `markdown_to_html` | CommonMark |

Deux classes portent le même nom dans deux paquets, et `symfony-content` comme
`symfony-template` déclarent une dépendance markdown dans leur `composer.json`.

Mesuré dans le conteneur d'un consommateur, sur un tableau à barres verticales :

```
CommonMarkConverter              -> pas de table
GithubFlavoredMarkdownConverter  -> table
```

`league/commonmark` est déjà installé et porte les deux. Il n'y a rien à ajouter
comme dépendance.

## Pourquoi ça remonte maintenant

Le bundle `home-habilis/doc-explorer`, dans doc-manager, affiche les documents
d'un système qualité : **157 des 158 fichiers contiennent au moins un tableau**,
et un seul document en porte sept. Rendus par CommonMark, ils sortaient en
rangées de barres verticales.

Faute de mieux, ce bundle a créé son propre
`HomeHabilis\DocExplorer\Service\DocumentRenderer` — une quatrième
implémentation, qui appelle `GithubFlavoredMarkdownConverter`. Elle est
volontairement minuscule et attend d'être supprimée.

## Ce qui est demandé

1. **Un seul propriétaire du markdown dans la suite**, et c'est
   `symfony-template`, qui possède déjà le convertisseur. Décider du sort de
   `symfony-content/src/Twig/MarkdownExtension.php` : sa fonction
   `markdown_file()` ne fait que lire un fichier, elle ne devrait pas s'appeler
   ainsi ni vivre à côté d'une dépendance markdown qu'elle n'utilise pas.
2. **Rendre les tableaux.** Passer à `GithubFlavoredMarkdownConverter` en
   gardant `html_input: strip` et `allow_unsafe_links: false`. GFM est un
   surensemble — tables, barré, listes à cocher, liens automatiques — donc pour
   les appelants existants c'est une correction. Si le changement sous leurs
   pieds vous gêne, une saveur en option et `markdown` inchangé par défaut.
3. **Le découpage front matter / corps**, qui n'a de maison nulle part et ne doit
   rien à une application : « ouvrir un `.md`, en tirer le yaml de tête et le
   reste ». Aujourd'hui réécrit dans `doc-explorer`
   (`DocumentReader::frontMatter()` et `::body()`).
4. **Le retrait d'une section par son titre** — le titre et tout ce qui suit
   jusqu'à un titre de rang égal ou supérieur — et le retrait des commentaires
   HTML. Le *mécanisme* est générique ; la *liste* des sections reste à
   l'application. Aujourd'hui dans `DocumentReader::withoutSection()`.
   À vous de dire si 3 et 4 vont dans `symfony-template`, dans `php-file`, ou
   dans un `php-markdown` qui n'existe pas encore.

## Ce qui n'est pas demandé

L'apparence. Un `<table>` sorti d'un markdown ne porte aucune classe, et
`symfony-design-system/assets/css/shapes/_content.scss` n'a **aucune règle pour
`table`** — le composant `data-table` a les siennes, qu'une conversion ne peut
pas produire. C'est un sujet pour l'agent du design system, signalé ici pour
mémoire et pas pour action.

## Le même problème en python

`markdown_document.py`, dans le bundle `home-habilis/pdf-generator`, fait déjà
les trois mêmes choses — front matter, commentaires HTML, sections retirées —
pour fabriquer les PDF. Lui non plus n'est pas dans un paquet. Le jour où la
liste des sections change, deux endroits dans deux langages doivent l'entendre.
Hors de votre périmètre, mais c'est la même histoire.

## Ce qui attend en aval

Une fois le paquet publié, il reste à nettoyer `doc-explorer` dans doc-manager :
supprimer `DocumentRenderer`, et faire passer `DocumentReader` par ce que vous
aurez écrit. L'opérateur décidera si c'est vous ou l'agent de app-board qui s'en
charge.
